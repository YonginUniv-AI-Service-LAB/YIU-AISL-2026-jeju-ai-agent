# 3. 결과 설명자료

## 3-1. 문제 정의
제주 소상공인의 경영 악화는 이미 여러 조사로 확인되어 있지만, 점주가 실제로 막히는 지점은 "그래서 우리 가게는 무엇을 해야 하나"입니다.
- 손님이 줄었을 때 **동네 전체가 줄었는지, 우리 가게만 줄었는지** 알기 어렵습니다. 읍면동 유동인구는 공개되어 있지만, 일별 원자료를 받아 기간을 맞춰 비교하는 일은 점주가 직접 하기 어렵습니다.
- 줄어든 이유가 **계절이나 비 때문인지** 구분하기 어렵습니다.
- 무언가를 바꿔 봐도 **효과가 있었는지 판단할 기준**이 없습니다.

이 에이전트는 공공데이터로 원인을 먼저 가르고, 점주의 예산·인력 안에서 **2주짜리 실험 하나**를 측정 지표·중단 기준과 함께 제안하고, 2주 뒤 결과를 점검합니다.

## 3-2. Agent 구조
LangGraph 상태 그래프 하나로 구성했고, 노드는 정해진 형식(`contracts.py`)으로만 데이터를 주고받습니다.

```
질문 + 가게 정보 + 주문 12주
 → [B] 질문 이해·조건 추출 ── 빠진 조건 → 되묻기
 → [A] 데이터 적합성 판정 F1~F7 (적합 / 범위 축소 / 판정 불가)
 → [A] 분석: 동네 흐름(직전·전년·강수) vs 내 가게 → 진단 4유형
 → [B] (재방문이면) 지난 실험 점검
 → [C] 실험 설계: 카탈로그 15개 → 예산·인력 필터 → 추천 1 + 대안 2, 지원제도
 → [C] 리포트 작성 → [C] 검증(숫자 재계산·근거 번호·금지 표현)
       └ 걸린 문장은 다시 쓰기(최대 2회) → 그래도 걸리면 템플릿으로 되돌리거나 제거
 → [B] 완료·세션 저장(실험이 있을 때만 재방문 코드 발급)
```

| 역할 | 담당 | 판단 주체 |
|---|---|---|
| 질문 이해 | B | LLM + 코드 검사(실패 시 규칙) |
| 적합성 판정·계산·진단 | A | 코드(규칙) — 같은 입력이면 같은 결과 |
| 실험 선택·리포트·검증 | C | 카탈로그·규칙, 문장 다듬기만 LLM(선택) |
| 화면·세션 | B | 코드 |

## 3-3. 주요 기능
1. **동네 흐름 대비 내 가게 진단**: 같은 기간의 읍면동 방문인구 변화와 가게 영업일당 주문 변화를 비교해 동반 하락형 / 나만 하락형 / 계절·날씨형 / 판단 불가로 분류
2. **데이터 적합성 판정**: 답하기 전에 "지금 데이터로 답해도 되는가"를 규칙으로 판정하고, 범위를 줄인 이유를 결과 맨 위에 안내
3. **2주 실험 카드**: 드는 돈, 추가 인력, 기간, 확인 방법, 그만둘 기준. 관련 지원제도(공식 출처 7건 중 최대 3개)
4. **2주 뒤 재방문 점검**: 6자리 코드로 다시 오면 실험 전·후 2주를 비교(±5% 기준, 단일 점포라 효과를 확정하지 않음)
5. **라이브 모드**: 키가 있으면 점주 기록 시기에 맞춰 동네 데이터를 API로 불러오고, 해시와 함께 동결해 재현 가능
6. **장애에 강한 흐름**: LLM·API가 실패해도 규칙 기반·스냅샷으로 끝까지 답함

## 3-6. 센터 활용 방안
1. **상담 도구**: 센터 상담원이 점주와 함께 질문과 12주 기록을 입력하고 리포트를 같이 읽습니다. 데이터를 찾고 기간을 맞추는 일은 에이전트가 합니다.
2. **읍면동 흐름 브리핑(확장)**: 같은 계산 엔진으로 최근 방문인구가 크게 변한 읍면동을 요약해, 지역별 상권 변화를 먼저 파악하는 보조 지표로 쓸 수 있습니다.
3. **운영 부담이 작음**: GPU·서버 없이 센터 PC 한 대(Docker 또는 Python)에서 동작하고, 스냅샷 해시와 실행 기록으로 센터가 결과를 다시 검증할 수 있습니다. 데이터는 `tasks.py snapshot` 한 명령으로 새 기준일로 갱신합니다.
